## 三、架构冗余与精简观察

1. **tech_chain 六子链 vs chains.py 九链**：两套链定义并存。v6.3 已澄清定位（tech_chain 是"加情报不加限制的并行情报线"）。中期看应合并为统一链注册表（chains.py 为主，tech_chain 退化为情报插件），减少双写漂移——**建议保留现状，WFA 周期外不做重构**（改动面大、决策语义零收益）。
2. **report.py（MD）+ report_html.py（双渲染器）**：同源双写，v3 各章节已出现"MD 有 HTML 无"的轻微漂移。**建议收敛为 HTML 单一渲染 + MD 由 HTML 降级导出**（低优先级）。
3. **hero_art.py 内嵌图片**：原 928KB（财神爷图占 700KB+）。本次换老虎图后降至 155KB（b64），零外链纪律与体积兼得。
4. **demo provider 双轨**：必要资产（测试确定性），非冗余。
5. **governance/ 整个 TS 底座随仓库分发（4.9MB）**：对"只用 Python 内核"的用户是冗余，对"全家桶"用户是必需。**建议保留单仓库，QUICKSTART 明确两条使用路径**（内核单用 / 全栈）。

## 四、业务视角总评

这套系统最像机构的地方不是评分体系，而是三句话：**拿不到真数据就诚实失败、改了参数要过统计检验、两本账每天互相对账**。本次真实运行暴露的 4 个问题全部发生在"协议的缝隙"里（None 语义、镜像口径、能力声明、新鲜度），而不是评分逻辑里——这是好消息：决策核心在真实数据下行为符合白皮书设计（MRS\* 5.7 撕裂降速、IBB 差 0.04 未入池不放水、轻仓通道标的全部轻仓）。真正欠缺的在外围：**LLM 点亮的叙事维度、治理底座的事件消费、官网发布环**——三者都是工程接线，不是交易逻辑。
