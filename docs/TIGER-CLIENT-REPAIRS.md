`governance/.workloom-client-foundation.json` 和原始 `verify-client-foundation-consumer.mjs` 保留审计基线的字节内容。修复登记独立保存每个受管文件的原始摘要、修复后摘要、修复提交、问题卡及对应测试摘要；它没有声称这些改动已经发布为新的上游 UI 版本。每项 `sourceCommit` 指向实际包含对应修复字节的既有提交，独立验收回读该提交的文件并核对摘要。同一文件涉及后续问题卡时，保留原卡归属并在 `reason` 中说明追加修复，校验器同时要求相关测试。

从仓库根目录运行：

```bash
node scripts/ci/verify-tiger-client-repairs.mjs
node --test tests/client-repair-provenance.test.mjs
```

校验器先执行原基座的完整检查，再核验本任务登记。只有校验器逐项列出的精确路径、匹配摘要的修复及各自绑定的测试可以被接受。其他文件差异、缺失文件、执行模式、版本、非法路径、符号链接及新增运行时代码仍然阻断。登记的基座 state 和校验器摘要也必须相符。原摘要不能被直接替换为修复摘要，测试文件不能省略。

这是一份本仓修复来源记录，授权事实来自当前用户请求与该任务的代码审查、实测；JSON 字段不构成身份认证或额外业务授权。它不允许实盘、真实资金或客户外发，也不改变舰队登记、实验车道或基座分发策略。适用范围仅为 [issue 24](https://github.com/geniusdapeng-collab/workroom-tiger/issues/24)／[PR 25](https://github.com/geniusdapeng-collab/workroom-tiger/pull/25) 中登记的上述修复。

后续修改任何已登记文件都需要重新审查、实际回归和更新精确摘要。基座升级会使旧版本／state 摘要绑定失效，届时必须检查新版本是否已包含修复，删除已合入上游的登记或重新评审剩余差异。不得扩大通配路径、伪造上游版本，或把本仓修复登记当作跨仓同步源。
